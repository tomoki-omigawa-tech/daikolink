# スプリント計画（Week 22〜24）

## 前提
| 項目 | 内容 |
|---|---|
| 期間 | 3スプリント × 1週間（Week 22・23・24） |
| 体制 | 1人（プロダクトオーナー・スクラムマスター・開発者を兼任） |
| 稼働 | 1週間あたり約35時間（1日5時間 × 7日） |
| 見積もり単位 | 1SP ＝ 1時間（`01_user-stories.md` のバックログを使用） |
| 計画した量 | Must 83SP ＋ バッファ約22SP ＝ 105時間 |

1人開発なので、スクラムのイベントは次のように行う。

| イベント | いつ | やること |
|---|---|---|
| スプリントプランニング | 各スプリント Day 1 の最初（30分） | バックログからタスクを選び、カンバンの TODO に並べる |
| デイリースクラム | 毎日の作業開始時（5分） | 「昨日やったこと / 今日やること / 困っていること」を Issue のコメントか日報に書く |
| スプリントレビュー | 各スプリント Day 7（30分） | 本番またはローカルで動作確認し、完了の目安を満たしたか確認する |
| レトロスペクティブ | レビューの後（15分） | KPT で振り返り、`04_retrospective.md` に追記する |

**完了の定義（Definition of Done）**：
受け入れ基準を満たす / Feature テストがある / lint・test の GitHub Actions が通る / PR を main にマージ済み

**WIP制限**：In Progress は2つまで（1人開発のため教材の3つより絞る）

## 遅れたときのルール
- スプリントの途中で遅れが分かったら、**Must の範囲は変えずに** 次のスプリントのバッファで吸収する
- バッファを使い切りそうなときは、スプリント3の Should をやめる（Must を削らない）
- 新しく出た要望は Could / Won't に追記し、MVP 完成後に検討する（要件定義書 9.4 のルール）
- 各スプリントの完了SP（ベロシティ）を記録し、次のスプリントの計画量を調整する
